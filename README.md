# REST_Responses
Takes the hassle away of setting up your HTTPResponse objects in microflows

## How to use
The best way to get started is to look at an example.
An example can be found in the example folder in the module. It contains a microflow with several http response microflow actions.

To get the example to work you simply need to:
- copy the example folder to a custom module 
- include all contents into your project
- send request to the endpoint of the example published rest service

## Siemens Guidelines
From version 3.0.0 onwards, the HTTP responses defined here are complient with the Siemens API Guidelines. The Siemens Guidelines offer a clear and concise guide on response handling. They have been incorporated into the Mendix API Guidelines. Read more here:
- Siemens Guidelines: https://developer.internal.siemens.com/guidelines/api-guidelines/rest/index.html
- Mendix Guidelines: https://mendix.atlassian.net/wiki/x/AYBPeQ

The Siemens guidelines describe that only the most commonly used HTTP responses should be used when handling a client's request. In addition, some of the responses are issued by the Mendix runtime or by the API Gateway. These responses are not defined here. In short, the following responses are defined in this module:
- 200, 201, 202, 204, 207
- 301, 303, 304
- 400, 401, 404, 406, 409, 410, 412, 415
- 500

The old java actions are still there for backwards compatability. However they should only be used for maintenance on existing API's. Use the new Siemens compliant java actions if
- You're building a new API
- You're updating your existing API to a new major version
- You're registering your API on the API Gateway

## Properties
The definition of the HTTP responses has been abstracted away in a suite of java actions. They are exposed as microflows. In your processing logic, create a new HttpResponse object or make sure an HttpResponse object is defined as an import parameter. Add a blank action to your logic, right-click and select 'Set type of action'. Scroll down to the HTTP Responses section and select the response you require. Fill out the properties in the popup box. See below for more information on the use of the properties.

### Content
A series of java actions have been implemented to help you construct the Content attribute of the 2xx response.
- Get_Metadata - returns a Metadata object with the parameters set on an associated Page object
- Get_Links_Offset - returns a Links object with offset based pagination URL's
- Get_Root - returns a Root object with Data, Metadata, and Links associated with it. Use this in your export mapping

When calling Get_Root, exactly one of Data or DataList must be supplied, or the action throws an error.

If your `200` response calls for an array of Data objects to be returned, pagination is implied. In this case when calling Get_Root Metadata and Links should not be empty.

In your implementation module allow all non-peristent entities that you use to return data inherit from this module's Data object. Copy one of the JSON examples in folder 'Example' and adjust the Data object or array, according to your requirements. Use this adjusted JSON structure as the basis for your export mapping.

### Correlation ID
This is a UUID that the client receives in case of errors. It can be used for trouble shooting purposes.

If your API is registered at the API Gateway, a Correlation ID will be part of the forwarded request in a header. The name of the header that carries the Correlation ID as generated by the API Gateway is set in constant HeaderName_CorrelationId.

At the beginning of your processing logic, invoke the java action `Get_Request_CorrelationId` to get the Correlation ID from the request's headers. If the header can not be found, a Correlation ID will be generated. Use this ID every time you log an issue in the processing logic and make it part of the HTTP response.

### Error Code
An application specific error code. This code can be useful when trouble shooting an issue. The naming convention must be harmonized across the system, not per se across the platform. The codes do not have to be human readable but they do need to be documented.

### Documentation Link
Don't let the client guess why the request failed. All client errors should be documented in the API specs. In addition, validation of data should be documented in the public documentation at docs.mendix.com. Provide a link to the documentation where users of a client can learn more on why the request failed.

### Authentication schema
When issuing response `401`, a `WWW-Authenticate` header should accompany the response. This header will tell the client which authentication schema to use to get the proper authentication. Which schema to enter depends on the type of authentication you allow on your API endpoint. In most cases this will be the UAT Bearer token. In that case the header will read something like this:
```
WWW-Authenticate: Bearer realm="login.mendix.com", scope="my:scope1 my:scope2", error="invalid_token"
```
Read more about this here: https://www.iana.org/assignments/http-authschemes
